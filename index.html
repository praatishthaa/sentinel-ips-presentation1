01 / PROJECT OVERVIEW

One core. Two detection layers. A response path.

Sentinel IPS brings traffic inspection, behavioural scoring, network controls and administration into one lab prototype.

01 / INSPECT

Suricata IPS

Inline gateway inspects traffic, matches configured signatures, and writes structured events.

02 / DETECT

Random Forest ML

Scores per-source, two-second flow windows for suspicious behavioural patterns.

03 / RESPOND

SDN controller

Uses OpenFlow rules on OVS to block a source and restore access when unblocked.

Scope: a tested GNS3 lab prototype, not a production-validated universal intrusion detector.

08 / MACHINE LEARNING STRATEGY

Behaviour detection complements signatures.

SIGNATURE LAYER

Suricata

Matches configured known patterns and can support immediate inline response when a rule fires.

BEHAVIOUR LAYER

Random Forest

Scores flow behaviour in two-second, per-source windows to flag patterns that the current custom signatures may miss.

Why two-second windows?

A single short connection attempt may be ambiguous. Aggregating flow count, distinct destination-port count, packet/byte volume, SYN-only fraction, packet sizes and traffic rates gives the classifier more behavioural context.

The model excludes source IP and destination port as inputs to reduce shortcut learning. It cannot guarantee that the earliest packets of an attack will be stopped.

09 / LAB DATASET

Train on traffic that actually crossed the gateway.

Suricata flow records were labelled using the time intervals of controlled benign and attack phases.

ATTACK PHASES
  • Fast and slow port scans
  • SYN flood and UDP flood
  • ICMP flood
  • Repeated SSH login attempts
BENIGN PHASES
  • SSH sessions of different lengths
  • Ordinary UDP traffic
  • Slower ping traffic
  • HTTP requests where the temporary server was available

12 / DEMONSTRATIONS & TROUBLESHOOTING

What the live lab demonstrated.

SUCCESSFUL CORE LOOP
  • Normal pings succeeded
  • Source was added to the block list
  • Pings failed while blocked
  • Unblock restored connectivity
  • Slow-scan ML alert and block succeeded
KNOWN TEST LIMITS
  • UDP detection was inconsistent in some live runs
  • Flow records can be delayed or absent
  • Some benign classes initially had too few samples
  • ICMP flood needs a separate rate-based check
  • Topology and interface mapping required correction

Important engineering lesson

Suricata only sees traffic crossing its gateway. A running container, a configured GNS3 node and a visible GNS3 project are distinct states; verify the actual cable map, interfaces and live controller status.

15 / LIMITATIONS & NEXT STEPS

A credible prototype, with a clear path forward.

CURRENT LIMITATIONS
  • Synthetic traffic from a single lab and attacker
  • Small test-window counts for some classes
  • Limited benign web and ping coverage
  • ML response depends on flow-window timing
  • Simulated optical readings and devices
RECOMMENDED NEXT STEPS
  • Verify the ML tab with live events
  • Repeat the demonstration from a clean restart
  • Expand benign and independent test traffic
  • Validate false positives and response delay
  • Implement phone notifications, LDAP and NETCONF if required

Present results as recorded lab evaluation. Do not claim universal 99.9% accuracy, complete mobile deployment, or production hardware support.

16 / CONCLUSION

Detection becomes useful when it can drive a response.

01

Inspect

Inline Suricata provides configured signature detection and structured traffic records.

02

Learn

A lab-trained Random Forest adds behavioural scoring over flow windows.

03

Act

The Sentinel controller can enforce blocks through OpenFlow and restore connectivity.

The key contribution is a working, integrated lab prototype that combines signature-based inspection, ML inference, SDN enforcement and secure administration — while making its validation limits explicit.
